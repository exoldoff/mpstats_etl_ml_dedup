# Текущий пайплайн MPStats

Короткая карта текущего workflow. Основной пользовательский сценарий живет в локальной web-app `mpstats_app/` + `web/`; старый пакетный `pipeline/services/run_service.py` остается как технический путь по шагам 1-6.

## Общая схема

```text
Справочник категорий MP STATS.csv
  -> план задач: project + marketplace + category + year + month
  -> download_tasks / pipeline_runs в DuckDB

MPStats API
  -> raw CSV
  -> processed CSV
  -> classified CSV
  -> mpstats.duckdb: mpstats_products + cube_registry
  -> отчеты, выгрузки, качество данных
```

Единица работы в web workflow - задача за один срез: проект, маркетплейс, категория, год и месяц. Прогресс хранится в DuckDB, а промежуточные результаты лежат файлами в `data/projects/{project}/...`.

## Источники правды

- `Справочник категорий MP STATS.csv` - категории, маркетплейсы, фильтры MPStats и план выгрузок.
- `classifiers/rules.csv` - правила классификатора, редактируются через вкладку `Классификатор`.
- `classifiers/manual_overrides.csv` - ручные правки классификации, если файл есть и подключен в настройках.
- `mpstats.duckdb` - статусы запусков, задачи, реестр куба и сохраненные товарные строки.
- `data/projects/{project}/...` - рабочие raw/processed/classified/export файлы конкретного проекта.

## Web workflow по задачам

1. **Планирование запуска**

   Web-app читает настройки проекта и справочник категорий, создает `pipeline_run` и набор `download_tasks`. Каждая задача получает пути для `raw_file_path`, `processed_file_path`, `classified_file_path` и статусы `download/process/classify/save`.

2. **Скачивание raw**

   Для категории используется cookie MPStats, для выгрузки по предмету - API token. Сервис вызывает MPStats, скачивает архив/CSV, распаковывает при необходимости и кладет исходник в `raw`. Если raw уже есть и перезапись не включена, задача просто помечается как `downloaded`.

3. **Обработка processed**

   Raw-файл читается в pandas. Сервис добавляет служебные колонки `Дата`, `Маркетплейс`, `Категория`, затем приводит колонки к общей схеме маркетплейса и парсит вес. Результат пишется в `processed.csv`.

   В старом пакетном пайплайне это было разнесено на шаги 2-4: enrich, standardize, parse weights. В текущем web workflow эти операции объединены внутри обработки одной задачи.

4. **Классификация classified**

   `processed.csv` читается в pandas и передается в `classifiers/engine.py`. Правила из `classifiers/rules.csv` сортируются по `priority` и применяются последовательно:

   - неактивные правила только попадают в отчет;
   - `category` ограничивает правило категорией, `*` или пустое значение означает все категории;
   - `match_type` поддерживает `contains`, `not_contains`, `regex`, `equals`, `startswith`, `otherwise`, `gt/gte/lt/lte`;
   - `conditions_json` добавляет несколько условий через `and/or`;
   - `mode=fill_empty` пишет только в пустые значения, `overwrite` перезаписывает;
   - `otherwise` тоже пишет только туда, где target-колонка еще пустая;
   - если target-колонки нет, она создается.

   После правил сервис убирает служебные колонки веса, добавляет текстовый месяц рядом с `Дата`, переименовывает `SKU`/`Название` под выходной контракт и применяет ручные override-правила. Итог пишется в `classified.csv`.

5. **Сохранение в DuckDB**

   `classified.csv` импортируется через временную stage-таблицу DuckDB в `mpstats_products`. Импорт добавляет метаданные среза: project, year, month, marketplace, source type, category key, source file и хэши строк. Если таблица уже есть, репозиторий расширяет схему под новые колонки и приводит типы так, чтобы новый CSV можно было вставить.

   Для защиты от дублей проверяется естественный ключ среза: проект, год, месяц, маркетплейс и категория. Без `overwrite_db` повторный срез не перезаписывается. С `overwrite_db` старый срез удаляется и загружается заново.

6. **Реестр куба**

   После успешного импорта обновляется `cube_registry`: сколько строк в срезе, откуда пришел classified-файл, хэш файла, период покрытия и флаги крупных категорий. Именно `cube_registry` показывает, какие месяцы и категории уже лежат в кубе.

7. **Отчеты, экспорт и качество**

   После сохранения основной источник для аналитики - DuckDB. Отчеты, плоские выгрузки, фильтры по категориям/периодам и проверки качества строятся SQL-запросами по `mpstats_products` и `cube_registry`.

## Где сейчас pandas, а где SQL

Pandas сейчас используется там, где workflow работает с промежуточными файлами:

- чтение raw CSV и подготовка `processed.csv`;
- применение классификатора к `processed.csv`;
- ручные override-правила;
- запись `processed.csv` и `classified.csv`.

DuckDB/SQL используется там, где данные уже становятся кубом приложения:

- хранение статусов запусков и задач;
- импорт classified-файлов в `mpstats_products`;
- дедупликация срезов;
- `cube_registry`;
- отчеты, экспорт CSV/XLSX и проверки качества.

## Почему классификация пока не SQL

Классификатор исторически сделан как pandas-движок над файлами. Он не просто фильтрует строки: правила идут строго по приоритету, создают колонки, учитывают пустые значения, поддерживают `otherwise`, ручные правки и отчет `candidate_rows/applied_rows`. Поэтому перенос в SQL возможен, но это отдельный SQL-компилятор правил, а не простая замена чтения CSV.

Безопасный путь ускорения: сначала сделать DuckDB-реализацию классификации для CSV, оставить pandas как fallback для XLSX/малых внешних файлов, затем тестом сравнить результат pandas и SQL на одном наборе входных данных и правил.
