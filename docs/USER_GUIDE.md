# MPStats Workflow: пользовательская документация

Эта инструкция описывает проект с точки зрения пользователя: что он делает, как запускать выгрузки, что означает каждый раздел интерфейса, как считаются итоговые показатели и где искать результат.

Документ намеренно не уходит в технические детали кода. Здесь важны рабочие сценарии, правила расчётов и смысл экранов.

## 1. Что делает проект

Проект помогает собрать данные из MPStats и довести их до удобного аналитического результата.

Основной поток такой:

1. Вы выбираете маркетплейсы, категории и месяцы.
2. Приложение скачивает отчёты из MPStats.
3. Данные приводятся к единому виду, даже если у разных маркетплейсов разные названия колонок.
4. Из названий товаров определяется вес или объём упаковки.
5. Считаются объём продаж в кг/тоннах и цена за кг.
6. Товары классифицируются по пользовательским правилам.
7. Результат сохраняется в файлы и в локальный куб/БД для поиска и повторного использования.
8. Для поддержанных категорий приложение автоматически запускает ML-дедуп после сохранения куба и готовит канонические SKU-группы.

Для категорий `Соус/Соусы`, `Кокосовое масло` и `Мыло` ML-дедуп входит в основной pipeline по умолчанию: приложение находит одинаковые SKU моделью, добавляет identity-группы для отчётов и заполняет отдельную таблицу канонических SKU.

Проект не меняет данные в MPStats. Он только скачивает отчёты, обрабатывает их локально и сохраняет результаты на вашем компьютере.

## 2. Основные понятия

**Проект**

Название выгрузки или направления работы. По нему приложение разделяет файлы, планы загрузки и записи в локальной БД. Например: `Мясо апрель`, `Мыло 2026`, `Сахар анализ`.

**Cookie MPStats**

Доступ к вашему текущему сеансу MPStats. Нужен для основного режима загрузки по категориям. Если cookie устарел, скачивание начнёт падать с ошибкой доступа. Cookie хранится только локально в настройках web-приложения и локальной DuckDB.

**MPStats API token**

Токен официального Analytics API MPStats. Нужен только для дополнительного режима загрузки по предмету у WB и Ozon. Для обычной загрузки по категории token не требуется.

**Категория**

Человекочитаемая группа товаров: например, `Мясо`, `Мыло`, `Сахар`.

**Путь MPStats**

Путь категории внутри MPStats. Для режима `По предмету` в этом же поле указывается ID предмета/ниши из MPStats.

**Фильтр**

Дополнительное ограничение внутри категории. Например, скачать только товары, где название содержит `жидкое`, или исключить товары, где название содержит `хозяйственное`.

**Умный план**

Список задач, который приложение создаёт перед запуском и сверяет с локальными файлами. Одна задача обычно равна связке:

```text
маркетплейс + категория/путь + год + месяц
```

**Куб**

Сохранённый набор обработанных данных по месяцам, маркетплейсам и категориям. В разделе `Данные` -> `Куб` можно увидеть, какие месячные срезы уже есть, и искать товары.

**Классификатор**

Набор правил, которые заполняют или исправляют колонки вроде `Подкатегория`, `Тип`, `Вид мяса`, `Бренд`.

## 3. Как запускать web-приложение

Основной пользовательский способ работы на macOS:

```text
MPStats Local App.command
```

Дважды кликните по этому файлу в корне проекта. Откроется локальное приложение в браузере.

При запуске `.command` создаёт локальное Python-окружение `.venv` в папке
проекта и проверяет зависимости, включая ML-дедуп зависимости `faiss-cpu`,
`sentence-transformers` и `torch`. Если чего-то не хватает, запускатель сам
выполнит установку из `requirements.txt` в `.venv`, затем соберёт frontend
при необходимости и откроет приложение. Системный Python при этом не
используется как runtime приложения.

На macOS эти ML-библиотеки могут приносить несколько копий OpenMP runtime
`libomp.dylib`. Запускатель заранее выставляет практический guard для
локального workflow — `KMP_DUPLICATE_LIB_OK=TRUE`, чтобы backend не падал с
`OMP: Error #15` при загрузке ML-дедупа.

При открытии браузера приложение показывает короткую стартовую заставку `MPStats Workflow` примерно на 5 секунд. Это только визуальный экран загрузки: настройки, проекты и последние запуски подгружаются как обычно, дополнительных действий от пользователя не требуется.

Пока открыто окно запуска, приложение работает. Чтобы остановить приложение, закройте окно запуска или нажмите `Ctrl+C` в нём.

На Windows используйте:

```text
MPStats Local App.bat
```

Этот запускатель не требует Node.js и админских прав. При первом запуске он создаёт локальную `.venv`, устанавливает Python-зависимости внутрь проекта и запускает приложение из готовой сборки `web/dist`. Если `web/dist` отсутствует, приложение на Windows не стартует: frontend нужно заранее собрать на компьютере, где есть Node.js, или взять уже подготовленную папку из проекта.

Все пользовательские действия выполняются через web-интерфейс. Старые отдельные CLI, notebook и desktop-GUI сценарии больше не поддерживаются.

## 4. Рекомендуемый рабочий сценарий

### Историческая загрузка

Используйте этот режим, когда нужно скачать диапазон месяцев: например, с января по апрель.

1. Откройте приложение.
2. Выберите режим `Историческая загрузка`.
3. Откройте `Проекты`, нажмите `Создать` и задайте имя проекта, если нужного проекта ещё нет.
4. Вставьте актуальный `MPStats cookie`. Если выбранные строки справочника грузятся `По предмету`, также вставьте `MPStats API token`.
5. Откройте вкладку `Категории`.
6. Отметьте нужные категории/пути.
7. Откройте `Умный план` и укажите период: с какого года/месяца по какой год/месяц.
8. Нажмите `Создать план`.
9. Проверьте вкладку `Умный план`.
10. Нажмите `Запустить`.
11. После завершения проверьте `Данные` -> `Куб` и `Данные` -> `Файлы`.

### Ежемесячное обновление

Используйте этот режим, когда уже есть сохранённый куб и нужно подтянуть следующий месяц.

1. Выберите режим `Ежемесячное обновление`.
2. Проверьте текущий проект в левом списке.
3. Вставьте актуальный cookie, если он устарел. Для предметных строк проверьте `MPStats API token`.
4. Нажмите `Синхронизировать новый месяц`.

Приложение смотрит, какой месяц уже сохранён последним, и создаёт план на следующий месяц. Если сохранённых месяцев ещё нет, берётся текущий месяц.

## 5. Разделы интерфейса

### Верхняя панель

Вверху выбирается режим работы:

- `Историческая загрузка` — ручной диапазон месяцев;
- `Ежемесячное обновление` — следующий месяц после последнего сохранённого;
- `Инструкция` — встроенная короткая справка внутри приложения.

В этой же панели есть авторская подпись `Made by @exoldoff` со ссылкой на GitHub и отдельная иконка Telegram.

В окне `Инструкция` есть кнопка `Полная инструкция`. Она открывает этот markdown-документ из проекта в отдельной вкладке браузера.

Основная навигация в центре оставляет только крупные разделы: `Проекты`, `Умный план`, `Категории`, `Данные`, `Классификатор`. Внутри раздела `Данные` отдельной короткой строкой выбираются `Куб`, `Отчёты`, `Файлы`, `Выгрузка` и `ML-дедуп`.

### Левая колонка: проект и настройки

Левую колонку можно свернуть кнопкой с иконкой панели. Это удобно после выбора проекта и настройки доступа: центральный рабочий экран становится шире, а настройки не остаются постоянно перед глазами.

#### Проект и доступ

Здесь задаются:

- `Текущий проект` — выбор из уже созданных проектов;
- `MPStats cookie` — доступ для основного скачивания отчётов по категориям;
- `MPStats API token` — доступ для дополнительного скачивания по предметам у WB и Ozon.

Новый проект создаётся только в разделе `Проекты` кнопкой `Создать`. После создания он появляется в списке слева и становится текущим.

Рядом с названиями полей есть значок `?`. Наведите на него курсор, чтобы увидеть, что именно меняет поле и когда его стоит использовать.

Кнопка `Сохранить настройки` сохраняет эти значения локально.

#### Настройки pipeline

Эти настройки управляют повторными запусками. По умолчанию блок компактный: видны только ключевые значения. Нажмите `Открыть`, чтобы изменить полный набор параметров.

У каждого параметра есть подсказка `?` рядом с названием. Она объясняет эффект настройки, безопасное значение по умолчанию и случаи, когда параметр стоит менять.

**Перескачивать raw**

Если выключено, приложение не скачивает заново файл, который уже есть. Если включено, raw-файл будет скачан повторно из MPStats.

**Пересобирать processed**

Если выключено, готовый обработанный файл используется повторно. Если включено, приложение заново пересчитает обработанный файл из raw.

**Перезаписывать БД**

Если выключено, уже сохранённый срез в кубе не дублируется. Если включено, приложение заменит данные для той же связки проект + месяц + маркетплейс + категория.

**Количество повторов**

Сколько раз повторить скачивание, если MPStats временно не ответил или отчёт не успел подготовиться.

**Таймаут, сек**

Сколько ждать подготовки отчёта MPStats.

**Пауза между запросами**

Пауза между скачиваниями. Обычно лучше не ставить ноль, чтобы не упираться в ограничения MPStats.

**Параллельные скачивания**

Настройка для режима загрузки. В обычной работе безопаснее оставлять `1`.

**Максимальный вес, кг**

Порог, после которого найденный вес считается подозрительным. По умолчанию `40 кг`. Всё, что выше, помечается как аномалия, если приложение не смогло исправить очевидную ошибку формата.

### Правая колонка: текущий запуск

Здесь видно состояние последнего плана:

- период;
- количество категорий;
- количество месяцев;
- всего задач;
- сколько готово;
- сколько ошибок;
- сколько осталось;
- текущий шаг.

Основные кнопки:

**Создать план**

Создаёт список задач, но ещё не скачивает данные. В историческом режиме кнопка активна только после выбора категорий и корректного периода.

**Запустить**

Запускает ожидающие задачи и задачи с ошибками. Недоступна, если плана нет, задач нет или запуск уже идёт. Обычный запуск не открывает модальное окно: текущий шаг и прогресс видны в правой колонке `Текущий запуск` и в live-статусах строк `Умного плана`.

**Пауза**

Мягко останавливает выполнение между стадиями. Активна только во время выполнения. Уже начатая стадия должна завершиться, после этого план перейдёт в `пауза`, а незавершённые задачи останутся в плане.

**Остановить**

Останавливает текущий pipeline и переводит план в `остановлено`. Уже завершённые стадии и файлы остаются на месте, незавершённые задачи не продолжаются автоматически. Если потом нужно догрузить остаток, нажмите обычный `Запустить` для этого плана.

**Продолжить**

Продолжает незавершённый запуск. Активна только для плана на паузе.

**Повторить ошибки**

Запускает только задачи со статусом ошибки. Активна только если ошибки действительно есть.

**Собрать куб из готовых файлов**

Использует уже готовые обработанные/классифицированные файлы и сохраняет их в БД без повторного скачивания.

**Переклассифицировать куб**

Заново применяет текущие правила классификатора к processed-файлам выбранного плана, перезаписывает classified-файлы и заменяет соответствующие срезы в локальном кубе/БД.

**Переобработать исходники**

Берёт уже скачанные raw-файлы выбранного плана, заново создаёт processed-файлы с парсингом веса и расчётами, затем классифицирует их и заменяет соответствующие срезы в локальном кубе/БД. Старые processed/classified-файлы по задачам плана удаляются и заменяются новыми. Raw-файлы не скачиваются повторно; если raw-файла нет, задача завершится ошибкой.

**Синхронизировать новый месяц**

Создаёт и запускает план на следующий месяц после последнего сохранённого месяца.

### Вкладка `Умный план`

Для исторической загрузки период выбирается именно здесь, перед созданием плана. Это не настройка проекта: один и тот же проект можно догружать разными периодами.

В режиме `Ежемесячное обновление` год и месяц не выбираются вручную. Приложение смотрит registry куба и берёт следующий месяц автоматически.

### Последние планы

Список последних созданных планов. Можно открыть старый план, посмотреть задачи, ошибки и продолжить работу.

Кнопка с корзиной удаляет сам план и его задачи из локальной DuckDB. Файлы проекта и уже сохранённые срезы куба при этом не удаляются. Выполняющийся план сначала нужно поставить на паузу или дождаться завершения.

## 6. Вкладка `Категории`

На этой вкладке выбираются категории для плана загрузки.

Категории подтягиваются из справочника категорий. Они сгруппированы по названию категории, внутри группы могут быть разные маркетплейсы, пути, периоды и фильтры.

В строке категории видно:

- маркетплейс;
- путь MPStats;
- признак `FBS`, если он включён;
- период активности, если он задан.

Можно выбрать:

- отдельный путь;
- всю группу категории кнопкой на заголовке группы;
- несколько категорий сразу.

Поиск ищет по названию категории, маркетплейсу, пути и периоду.

## 6.1. Табличные фильтры и сортировки

В таблицах приложения заголовок каждого столбца открывает меню как в Excel:

- `А-Я` / `Я-А` сортирует строки по выбранному столбцу;
- поле `Текст` оставляет строки, где значение столбца содержит введённую фразу;
- блок `Список` позволяет выбрать конкретные значения через чекбоксы;
- `Очистить` сбрасывает фильтр текущего столбца;
- `Сбросить` над таблицей убирает все фильтры и сортировку.

Эти фильтры работают в предпросмотрах и таблицах интерфейса: умный план, файлы, куб, предпросмотр БД, предпросмотр выгрузки, справочник и классификатор.

## 7. Редактор `Справочник`

Справочник — это главный список категорий и путей MPStats. Приложение использует CSV-файл:

```text
Справочник категорий MP STATS.csv
```

Excel-дубликаты не считаются источником правды. Если нужно менять категории, откройте `Справочник` в левом блоке `Правила и справочник` или правьте этот CSV.

Справочник общий для всех проектов на этом компьютере: он не делится по проектам. При открытии списка категорий приложение перечитывает этот локальный CSV в каталог DuckDB, поэтому изменения в файле применяются к любому выбранному проекту.

Если в редакторе `Справочник` есть несохранённые правки, при уходе из раздела или перечитывании CSV приложение спросит, сохранить изменения, сбросить их или остаться в редакторе.

### Поля справочника

**Активна**

Если выключено, строка не участвует в выборе категорий.

**Категория**

Человекочитаемое название категории. Оно потом попадает в итоговые данные.

**Маркетплейс**

Один из поддерживаемых маркетплейсов: Ozon, WB, Яндекс.Маркет.

**FBS**

Признак FBS для выгрузки. По умолчанию включён для маркетплейсов, где доступен, но его стоит выключать у нефудовых категорий. У Яндекс.Маркета FBS не используется: в редакторе справочника чекбокс заблокирован в выключенном состоянии.

**Тип выгрузки**

Переключатель `По категории / По предмету`.

- `По категории` — основной режим по умолчанию. Он использует текущую категорийную загрузку MPStats и `MPStats cookie`.
- `По предмету` — дополнительный режим для WB и Ozon через Analytics API и `MPStats API token`. У Яндекс.Маркета этот режим недоступен: при выборе Яндекса строка принудительно остаётся `По категории`.

В таблице предпросмотра справочника и в списке категорий рядом со строкой показывается клейм `по категории` или `по предмету`. Старые строки CSV без колонки `Тип выгрузки` считаются `По категории`.

**От / До**

Период активности строки. Если задано `От`, категория будет участвовать только начиная с этого месяца. Если задано `До`, только до этого месяца включительно.

Примеры:

- `2026` — весь 2026 год;
- `2026-03` — март 2026;
- `03.2026` — март 2026;
- `март 2026` — март 2026.

**Путь / ID предмета**

Для `По категории` это основной путь MPStats. Для `По предмету` это ID предмета/ниши MPStats.

**Фильтр по названию**

Дополнительное ограничение внутри пути. Можно задать одно или два условия:

- `Содержит` — оставить товары, где название содержит фразу;
- `Исключает` — исключить товары, где название содержит фразу.

Если условий два, между ними выбирается связь:

- `И` — должны выполниться оба условия;
- `ИЛИ` — достаточно одного условия.

**Комментарий**

Поле для рабочих заметок.

### Как добавить новую категорию

1. Откройте `Справочник` в левом блоке `Правила и справочник`.
2. Нажмите `Добавить`.
3. Выберите тип выгрузки: обычно оставьте `По категории`; для WB/Ozon можно выбрать `По предмету`.
4. Заполните категорию, маркетплейс, период, путь или ID предмета и фильтр.
5. Нажмите `Сохранить CSV`.
6. Перейдите в раздел `Категории`.
7. Нажмите `Обновить справочник`, если новая строка ещё не появилась.

### Как временно отключить категорию

1. Откройте строку в редакторе `Справочник`.
2. Выключите `Активна в приложении`.
3. Нажмите `Сохранить CSV`.

После этого строка останется в справочнике, но не будет участвовать в новых планах.

## 8. Как создаётся умный план

План строится из выбранных категорий и периода.

Для каждой активной выбранной строки справочника приложение берёт все месяцы из выбранного диапазона. Если у строки есть `От` или `До`, месяцы вне этого периода пропускаются.

Итоговая задача создаётся для каждой комбинации:

```text
категория/путь + маркетплейс + месяц
```

Например, если выбрано 3 пути и период 4 месяца, будет до 12 задач. Если у части путей ограничен период активности, задач будет меньше.

Если для строки задан фильтр, он применяется при скачивании из MPStats. Если включён FBS, он тоже учитывается при запросе.

## 9. Вкладка `Умный план`

Это основная вкладка приложения при открытии web-app. Она показывает задачи текущего плана, сверяет их с локальными файлами проекта и отдельно показывает матрицу наполнения куба.

В верхней части есть:

- сводка по статусам текущего плана;
- карточка `В БД` с общим количеством срезов в кубе текущего проекта, независимо от выбранного плана из истории;
- рекомендованное действие;
- матрица куба по категориям и маркетплейсам;
- фильтры `Все`, `Готовые`, `Нет файлов`, `Устарели`, `Ошибки`, `Неполные`.

### Матрица куба

Матрица строится по уже сохранённым срезам из `Данные` -> `Куб`.

Строки — категории, колонки — маркетплейсы. В колонке маркетплейса эталоном считается последний месяц, который уже есть в кубе для этого маркетплейса. Ячейка показывает:

- `✅ ММ.ГГГГ`, если для категории есть актуальный срез за последний месяц этого маркетплейса;
- `❌ ММ.ГГГГ`, если срез есть, но он отстаёт от последнего месяца маркетплейса;
- `❌ нет данных`, если для категории и маркетплейса в кубе нет ни одного среза.

Так сразу видно, какие связки категория + маркетплейс надо доскачать или пересобрать.

### Тяжёлые категории и отчёты

Если категория или отдельный месячный срез становится слишком большим, приложение помечает его как `тяжёлая`. Сейчас ориентиры такие:

- срез от 250 000 строк;
- категория от 1 000 000 строк суммарно по проекту.

Тяжёлый режим не удаляет raw/processed/classified-файлы и не меняет расчёты. Он меняет рекомендуемый способ анализа: вместо открытия миллионов сырых строк в Excel используйте `Данные` -> `Отчёты`.

Во вкладке `Куб` у таких срезов появляется режим `тяжёлая` и причина. Во вкладке `Отчёты` видно список тяжёлых категорий, доступные отчётные таблицы и время последней сборки отчёта.

Доступные отчёты:

- `Категория по месяцам` — продажи, выручка, объём и цены по категории, маркетплейсу и месяцу;
- `Бренды по месяцам` — те же метрики с разрезом по брендам;
- `Классификация по месяцам` — разрез по колонкам классификатора, если они есть в кубе;
- `Топ SKU` — агрегированный топ товаров по выручке и продажам без выгрузки raw-строк.

Excel-файлы из `Отчёты` уже подготовлены для анализа и сводных таблиц. Это основной способ работать с большими категориями.

Умный план сравнивает желаемые задачи `маркетплейс + категория + месяц` с рабочими файлами:

- `raw`;
- `processed`;
- `classified`;
- сохранённым срезом в `Данные` -> `Куб`.

В таблице есть стадии:

**Скачивание**

Получение raw-файла из MPStats.

**Обработка**

Приведение колонок к единому виду, расчёт веса, объёма и цены за кг.

**Классификация**

Применение правил классификатора.

**БД**

Сохранение результата в локальный куб.

### Статусы умного плана

**готово**

Есть актуальный classified-файл или срез уже сохранён в `Данные` -> `Куб`.

**нет файлов**

Для задачи пока нет локальных файлов. Обычно нужно запустить скачивание.

**устарело**

Один из upstream-файлов новее результата: например, `raw` новее `processed`, `processed` новее `classified` или `classified` новее сохранённого среза БД.

**ошибка**

Последний запуск задачи упал. Текст ошибки видно в строке.

**неполно**

Есть только часть файлов: например, `raw` уже скачан, но `processed` или `classified` ещё не собраны.

### Стадии pipeline

**ожидает**

Задача создана, но ещё не выполнялась.

**скачивание / скачано**

Файл скачивается или уже скачан.

**обработка / обработано**

Файл обрабатывается или уже обработан.

**классификация / классиф.**

Применяются правила классификатора или результат уже готов.

**сохранение / в БД**

Данные сохраняются или уже сохранены в куб.

**ошибка**

Задача упала. Текст ошибки видно в строке.

**нет данных**

MPStats вернул пустой файл или в нём нет строк.

**пропуск**

Приложение не выполняло стадию, потому что нужный файл или сохранённый срез уже есть.

### Фильтры задач

Над таблицей можно быстро оставить:

- все задачи;
- готовые;
- задачи без файлов;
- устаревшие;
- задачи с ошибками;
- неполные.

Для одной задачи есть кнопка `повтор`. Она перезапускает только выбранную строку.

## 10. Что происходит при обработке данных

Обработка превращает разные выгрузки маркетплейсов в единый формат.

### Единые основные колонки

После стандартизации приложение приводит данные к таким базовым полям:

- `Дата`;
- `Маркетплейс`;
- `Категория`;
- `SKU`;
- `Бренд`;
- `Название`;
- `Продажи`;
- `Продавец`;
- `Средняя цена`;
- `Выручка`.

Если у маркетплейса колонка называется иначе, приложение приводит её к общему названию.

### Дата

В помесячной загрузке дата ставится как первый день месяца. Например, для апреля 2026:

```text
01.04.2026
```

Это нужно, чтобы все строки месячного отчёта имели понятную привязку к периоду.

### Бренд и продавец

Бренд и продавец приводятся к нижнему регистру и очищаются от лишних пробелов. Это помогает одинаково считать и искать значения, которые в исходных файлах отличаются только регистром.

### Продажи

Продажи приводятся к числу. Пробелы, неразрывные пробелы и запятые в числах очищаются.
После этого pipeline отбрасывает строки без продаж и нижний хвост по продажам:
внутри каждого месячного среза остаются строки с `Продажи` не ниже общего
минимума `15` продаж. Это убирает товары без фактического спроса и самый
малозначимый хвост до классификации, сохранения в куб и research-ноутбуков.

## 11. Как рассчитывается вес и объём

Вес определяется из названия товара.

Приложение ищет в названии:

- граммы: `г`, `гр`, `g`, `грамм`;
- килограммы: `кг`, `kg`, `килограмм`;
- миллиграммы: `мг`, `mg`;
- миллилитры: `мл`, `ml`;
- литры: `л`, `l`, `литр`.

Для расчётов объёма жидкости условно переводятся в килограммы:

```text
1 л = 1 кг
1000 мл = 1 кг
```

### Упаковки и наборы

Если в названии указано несколько штук, приложение отдельно сохраняет вес одной штуки и суммарный вес упаковки.

Примеры, которые понимаются:

```text
3 x 175 г  -> Вес, кг (ед.) = 0.175; Вес, кг = 0.525
175 г x 3 -> Вес, кг (ед.) = 0.175; Вес, кг = 0.525
3 шт по 175 г -> Вес, кг (ед.) = 0.175; Вес, кг = 0.525
3 шт - 175 г -> Вес, кг (ед.) = 0.175; Вес, кг = 0.525
16 упаковок по 600 г -> Вес, кг (ед.) = 0.6; Вес, кг = 9.6
```

Если в названии найдено несколько весов, приложение выбирает наиболее вероятный вес единицы и суммарный вес: сумму упаковки, если она распознана, или максимальный одиночный вес.

### Контроль аномалий

После извлечения веса приложение проверяет значение.

Если вес не найден, равен нулю или выглядит некорректно, строка получает признак аномалии.

Если вес одной единицы выше настройки `Максимальный вес, кг`, он тоже считается подозрительным. По умолчанию порог — `40 кг`.

В некоторых случаях приложение пытается исправить очевидный сдвиг в записи. Например, когда в названии литры или миллилитры записаны без десятичной точки. Если исправить безопасно не получается, вес оставляется пустым, а строка помечается как аномальная.

### Выходные колонки расчёта веса

**Вес, кг сырой**

Первое найденное значение веса одной единицы до проверки.

**Вес, кг (ед.)**

Итоговый вес одной единицы после проверки и исправлений.

**Вес, кг**

Суммарный вес упаковки с учётом мультипака. Именно он используется в расчётах объёма и цены за кг.

**Вес аномалия**

Признак, что вес нужно проверить вручную.

**Вес причина**

Короткое объяснение: всё хорошо, вес не найден, слишком большой вес, исправлен формат и т.д.

**Объем, кг**

Расчёт:

```text
Продажи, шт × Вес, кг
```

Если вес не найден, объём считается как `0`.

**Объем, т**

Расчёт:

```text
Объем, кг / 1000
```

**Цена за кг**

Расчёт:

```text
Средняя цена, руб / Вес, кг
```

Если вес не найден или равен нулю, цена за кг остаётся пустой.

## 12. Как работает склейка файлов

Склейка объединяет обработанные файлы в общий результат.

Перед сохранением приложение:

1. Приводит колонку продаж к числу.
2. Оставляет строки, где продажи больше `0`.
3. Убирает строки, где продажи `40000` или больше.
4. Убирает полностью одинаковые дубли строк.

Ограничение по продажам нужно, чтобы убрать пустые строки и явно подозрительные выбросы.

## 13. Как работает классификатор

Классификатор — это набор правил вида:

```text
если условие выполнено -> записать значение в нужную колонку
```

Пример:

```text
Если Название содержит "жидк"
то Подкатегория = "Жидкое"
```

Правила редактируются во вкладке `Классификатор` и сохраняются в:

```text
classifiers/rules.csv
```

При открытии вкладки редактор не выбирает правило автоматически. Сначала выберите строку в списке правил или нажмите `Создать новое`.

Руками писать JSON не нужно: интерфейс собирает условия сам.

### Из чего состоит правило

**Правило активно**

Если выключено, правило сохраняется, но не применяется.

**Для категории**

Ограничивает правило одной или несколькими категориями. В редакторе правила категории выбираются чекбоксами из CSV-справочника категорий. Если выбрано `Все`, правило применяется ко всем категориям.

В web-pipeline каждый processed-файл относится к одной категории, поэтому перед применением правил классификатор заранее пропускает правила явно чужих категорий. Затем для оставшихся правил он всё равно отбирает строки выбранных категорий и только потом проверяет условия. Это не меняет результат, но ускоряет обработку больших файлов.

В списке правил категория показывается отдельной колонкой `Категория`, а не добавляется к тексту условия.

**Порядок**

Чем меньше число, тем раньше применяется правило. Если несколько правил подходят к одному товару, порядок особенно важен.

**Условия**

Где искать и что искать. Например:

- в `Название` содержит `жидк`;
- в `SKU` равно `123456789`;
- в `Бренд` не содержит `no name`.
- в `Вес, кг (ед.)` меньше `10`;
- в `Вес, кг` больше `1`.

Можно добавить несколько условий и связать их через `И` или `ИЛИ`.

Условие `содержит` ищет обычный текст: символы `.`, `+`, `(`, `)`, `[`, `]`, `*`, `?` не считаются регулярным выражением. Для регулярных выражений используйте отдельный режим `regex`.

Для числовых колонок, например `Вес, кг` и `Вес, кг (ед.)`, доступны сравнения `>`, `>=`, `<`, `<=`. Значение можно писать как число или с единицей измерения: `10`, `10,5`, `10 кг`. Классификатор берёт числовую часть и сравнивает её как число.

Отдельный шаблон `если пусто` создаёт fallback-строку. Она читается так: если целевая колонка, например `Подкатегория`, всё ещё пустая после правил выше по порядку, записать указанное значение, например `Прочее`. Такая строка не ищет текст в `Название` или `SKU` и не должна оставлять пустыми классифицируемые колонки. Движок всегда применяет fallback только к пустым ячейкам целевой колонки, даже если в старом CSV для такого правила остался режим `перезаписать`.

**Куда записать**

Колонка, которую нужно заполнить или изменить. Например: `Подкатегория`, `Тип`, `Бренд`, `Вид мяса`.

**Что записать**

Значение, которое попадёт в выбранную колонку.

**Режим**

- `заполнить пустое` — значение записывается только там, где колонка пустая;
- `перезаписать` — значение записывается даже поверх уже заполненной колонки.

### Мясной справочник

Для категории `Мясо` колонка `Подкатегория` настроена по укрупнённому мясному справочнику. Правила пишут значения:

```text
Кулинария, Маринады, Крупнокусковые, Колбаски, Мелкокусковые,
Шашлык, Ребра крупнокусковые, Ребрышки маринадные,
Фарш, Порционные, Прочее
```

Если товар не попал в конкретное мясное правило, он получает `Прочее`. Более точные правила идут ниже по порядку и перезаписывают этот остаток: например, котлеты и биточки попадают в `Кулинария`, стейки/сатэ/каджун/маринады попадают в `Маринады`, шашлык попадает в `Шашлык`, а ребрышки в маринаде попадают в `Ребрышки маринадные`.

Для товаров с `Подкатегория = Колбаски` дополнительно заполняется колонка `Тип`. Возможные значения:

```text
Сосиски, Варёная колбаса, Сервелат (варёно-копчёная), Другое
```

Сосиски и сардельки попадают в `Сосиски`, варёные колбасы в `Варёная колбаса`, сервелат и варёно-копчёные позиции в `Сервелат (варёно-копчёная)`. Остальные колбаски, купаты, чевапчичи и люля-кебаб остаются в `Другое`.

### Быстрые шаблоны

Во вкладке `Классификатор` есть быстрые варианты:

- `по названию`;
- `по точному SKU`;
- `бренд из названия`;
- `если пусто`.

Они создают заготовку правила, которую остаётся заполнить.

Если в редакторе есть несохранённые правки правил, при уходе из вкладки приложение спросит, сохранить изменения, сбросить их или остаться в редакторе.

### Ручные правки SKU

Если нужно исправить конкретный товар после автоматической классификации, используйте блок `Ручные правки SKU` во вкладке `Классификатор`.

Правки сохраняются отдельно от обычных правил:

```text
classifiers/manual_overrides.csv
```

Одна ручная правка работает так:

```text
найти точное значение в колонке -> записать новое значение в нужную колонку
```

Обычно для точечного товара выбирайте:

- `Где искать` = `Артикул`;
- `Что искать` = конкретный артикул/SKU товара;
- `Куда записать` = `Подкатегория`, `Тип`, `Бренд` или другая итоговая колонка;
- `Режим` = `перезаписать`.

Для объединения нескольких SKU нажмите `Объединение SKU`. Шаблон создаёт правку в колонку `SKU-группа`: нескольким артикулам можно записать одно и то же значение, а затем выбрать эту колонку в выгрузке или отчёте. Если нужно физически заменить итоговое название SKU, в ручной правке можно указать `Куда записать` = `SKU`.

Ручные правки применяются после автоматических правил классификатора. Поэтому они сохраняют приоритет при повторной классификации куба и при обработке внешнего файла через блок `Внешний файл`.

### Внешний файл

Классификатор можно использовать отдельно от полной загрузки:

1. Откройте вкладку `Классификатор`.
2. В блоке `Внешний файл` выберите CSV или XLSX.
3. При необходимости включите `Сохранить копию XLSX`.
4. Нажмите `Обработать`.

Приложение создаст готовый CSV с применёнными правилами и ручными правками SKU, затем покажет первые строки результата.

В деталях шага классификации сохраняются тайминги фаз: чтение входного файла, применение правил, postprocess, ручные правки, запись CSV и, если включено, запись XLSX. Если маленький файл обрабатывается необычно долго, по этим значениям можно понять, где именно задержка.

В логах локального приложения дополнительно появляются строки `MPStats pipeline task timing` по стадиям `download`, `process`, `classify`, `save_to_duckdb` и `total`. В них есть `task_id`, `run_id`, проект, маркетплейс, категория, месяц, длительность, известное число строк/колонок и размеры raw/processed/classified файлов.

### Что меняется после классификации

В финальный classified-файл добавляется колонка `месяц` с короткой русской меткой месяца из `Дата`: `янв.`, `фев.`, ..., `дек.`. Она нужна для удобной фильтрации в сводных таблицах и попадает в куб/выгрузки как обычная колонка.

После классификации из финального пользовательского файла убираются служебные колонки контроля веса:

- `Вес, кг сырой`;
- `Вес аномалия`;
- `Вес причина`;
- `Объем, кг`.

Итоговый CSV при этом сохраняет пользовательские расчётные и классификационные колонки, включая `Вес, кг`, `Вес, кг (ед.)`, `Объем, т`, `Цена за кг`, `Подкатегория`, `Тип`, `Вид мяса`, `SKU-группа` и другие колонки, которые создали правила или ручные правки.

### Аудит производительности классификатора

При каждом применении правил классификатор пишет summary-лог `Classifier summary`: сколько правил загружено, сколько осталось после category-prefilter, какие target-колонки созданы, сколько правил и времени пришлось на каждую target-колонку, top-10 самых медленных правил и долю пустых значений в целевых колонках.

По умолчанию отдельный лог `Classifier rule timing` пишется только для правил медленнее 0.5 секунды. Для диагностики можно включить полный лог всех правил через переменную окружения:

```bash
MPSTATS_CLASSIFIER_VERBOSE_RULES=1
```

Порог медленного правила можно изменить так:

```bash
MPSTATS_CLASSIFIER_SLOW_RULE_SEC=0.2
```

Для диагностики медленной классификации есть отдельные скрипты. Они не меняют правила и production-логику, а создают benchmark-файлы в локальной папке:

```text
data/classifier_benchmark/
```

Быстрый профиль на mock-данных:

```bash
python3 scripts/profile_classifier.py --all-sizes
```

Benchmark на mock-данных и маленьком реальном sample, если в `data/projects` есть processed CSV:

```bash
python3 scripts/benchmark_classifier.py run --all-sizes
```

Большой запуск на 500 000 строк защищён отдельным флагом:

```bash
python3 scripts/profile_classifier.py --size large --include-large
python3 scripts/benchmark_classifier.py run --size large --include-large
```

Для проверки, что оптимизация не изменила классификацию, сравните старый и новый classified CSV:

```bash
python3 scripts/benchmark_classifier.py compare old_classified.csv new_classified.csv
```

Итоговый аудит текущего состояния описан в
`docs/archive/CLASSIFIER_PERFORMANCE_AUDIT.md`.

## 15. Раздел `Данные` -> `Куб`

Эта вкладка показывает, что уже сохранено в локальном кубе.

При сохранении среза в куб приложение дополнительно проверяет тот же фильтр
продаж и объёма: в товарную БД попадают только позиции с положительным
объёмом (`Объем, кг` или `Объем, т`) и с `Продажи, шт` не ниже общего
минимума `15` продаж. Это safety-net для старых или вручную загруженных

В таблице срезов видно:

- месяц;
- маркетплейс;
- категорию;
- количество строк;
- сколько дней месяца покрывает срез;
- дату совершения выгрузки;
- файл-источник.

Колонка `Дней` показывает покрытие в формате `загружено/всего`. Для прошлых месяцев приложение считает месяц полным. Для текущего месяца дата актуальности берётся по дню, когда срез был сохранён в куб: например, если майская выгрузка сохранена 28 мая, в кубе будет `28/31 · по 28.05.2026`.

### Как приложение защищается от дублей

При сохранении в БД приложение не даёт повторно загрузить уже существующий срез по связке `проект + месяц + маркетплейс + категория`. Категория проверяется по видимому названию из справочника/файла, а не только по внутреннему `category_key`, поэтому смена пути или id категории не создаёт дубль.

Если тот же срез уже был сохранён, обычный запуск помечает задачу как уже сохранённую и не добавляет строки повторно. Если включить `Перезаписывать БД`, старые записи для этой связки будут заменены.

Дополнительно для единого куба считается бизнес-отпечаток без `category_key`, source file и служебных metadata. Если одна и та же товарная строка пришла и из загрузки `По категории`, и из загрузки `По предмету` за тот же проект, месяц и маркетплейс, сохраняется первая загруженная копия, а последующая точная копия пропускается.

Если нужно исправить ошибочные правила классификатора или ручные правки SKU на уже загруженных данных, внесите изменения во вкладке `Классификатор`, откройте нужный план и нажмите `Переклассифицировать куб`. Перед запуском приложение автоматически сохранит несохранённые правила и ручные правки в CSV. Для этого у задач должны сохраниться исходные processed-файлы; приложение заново создаст classified-файлы и заменит эти месячные срезы в БД.

После нажатия `Переклассифицировать куб` открывается модальное окно прогресса: в нём видны статус запуска, текущий шаг, процент выполнения, сколько файлов нужно переклассифицировать, сколько уже переклассифицировано, сколько осталось, ошибки и переходы в `Умный план` или `Куб`. Первый шаг `Проверка processed-файлов` означает подготовку списка задач и проверку наличия входных processed CSV; если на этой ранней стадии возникает ошибка, запуск переводится в статус `ошибка`, а текст ошибки показывается в текущем шаге. Во время переклассификации classified-файлы и срезы БД заменяются по задачам плана, поэтому предпросмотр куба обновляется после статуса `готово`.

Если нужно пересчитать веса, объём, цену за кг или другие поля обработки из уже скачанных исходников, откройте нужный план и нажмите `Переобработать исходники`. Для каждой задачи приложение проверит raw-файл, удалит старые processed/classified-файлы, заново выполнит обработку, парсинг веса, классификацию и замену среза в БД.

В `Умном плане` задачи, которые прямо сейчас выполняются, показывают live-статус pipeline (`скачивание`, `классификация`, `сохранение` и т. п.) вместо обычной рекомендации вроде `устарело`. Обычный запуск и догрузка файлов идут без модального окна; прогресс остаётся в правой панели текущего запуска. Модальное окно прогресса используется для тяжёлых операций куба: сборки, переклассификации и переобработки.

Кнопка с корзиной в строке среза удаляет registry-запись куба и строки товарной БД для связки `проект + месяц + маркетплейс + категория`. Для удаления пачки срезов отметьте их чекбоксами и нажмите `Удалить выбранные`: приложение удалит выбранные registry-записи и строки товарной БД одним пакетным действием. Исходные raw/processed/classified-файлы остаются на диске, поэтому срез можно собрать заново кнопкой `Собрать куб из готовых файлов`.

## 16. Раздел `Данные` -> `ML-дедуп`

Эта вкладка показывает и при необходимости вручную перезапускает production ML-дедупликацию по данным, уже сохранённым в DuckDB. В обычном запуске smart pipeline ML-дедуп включён по умолчанию и выполняется после сохранения classified-файлов в куб.

ML-дедуп не скачивает MPStats заново и не меняет исходную таблицу `mpstats_products`: результат пишется в отдельные identity-таблицы `dedup_*` и в materialized-таблицу `mpstats_products_dedup` для просмотра и выгрузок.
На вход ML-дедупа дополнительно применяется тот же safety-фильтр, что и при сохранении куба: строки с `Продажи, шт` ниже `15` и строки без положительного объёма не попадают в SKU-node даже для старых срезов куба.

В v1 поддержаны категории:

- `Соус` / `Соусы`;
- `Кокосовое масло`;
- `Мыло`.

Перед запуском проверьте блок настроек модели:

- `Локальный путь модели` — путь к fine-tuned BGE cross-encoder весам на этой машине;
- `HF model id` — `exoldoff/bge-reranker-v2-m3-cross-encoder-marketplaces-rus`;
- `Embedding model` — модель для FAISS candidate retrieval;
- `Устройство` — `auto`, `cpu`, `mps` или `cuda`. На Mac с Apple Silicon `mps` использует Apple GPU через PyTorch/Metal; `cpu` принудительно считает на процессоре; `auto` оставляет выбор библиотеке;
- `K FAISS` — сколько ближайших соседей брать на SKU-node перед cross-encoder scoring. Меньше `K` ускоряет запуск, но повышает риск, что настоящий дубль не попадёт в candidate pairs и граф уже не сможет его склеить;
- `Batch embeddings` и `Batch scoring` — размеры батчей для embedding-модели и cross-encoder.

Production-профиль зафиксирован в приложении: `method=ft_bge_reranker_v2_m3`, default FAISS `K=30`, `threshold_strategy=threshold_weighted_cost`, `activation=sigmoid`. Порог применяется по категории: `Соус/Соусы` -> `0.917444`, `Кокосовое масло` -> `0.872321`, `Мыло` -> `0.930329`; общий `threshold_same=0.872321` остаётся fallback для неизвестного ключа категории. В каждом run и в edge-таблице сохраняется фактически применённый threshold и фактически выбранный `K`. Если fine-tuned модель недоступна, запуск завершается ошибкой; rule-based или zero-shot fallback не считается успешным результатом.

Инкрементальный cache включён всегда. Приложение хранит:

- identity-cache: уже найденную группу `node_id -> ML-группа товара / фасовки`;
- node embedding-cache: embeddings отдельных SKU-node в DuckDB;
- pair score-cache: score cross-encoder для пары SKU-node при той же модели и том же тексте пары;
- snapshot-cache: `data/projects/<project>/dedup_cache/<category>/<cache_key>/` с `embeddings.npy`, `node_ids.json` и `manifest.json` для полностью одинакового source/model.

При повторном запуске приложение сначала ищет текущие SKU-node в identity-cache. Если все node уже известны, ML-модели не запускаются: результат просто материализуется в `mpstats_products_dedup` с актуальными продажами/выручкой. Если появились новые SKU-node, FAISS query строится только от них: новые SKU сравниваются со старыми группами и между собой, а старые SKU сохраняют прежнюю группировку. Embedding-модель получает только node без сохранённого embedding, cross-encoder получает только пары без сохранённого score. FAISS index-файлы в v1 не сохраняются и не читаются, индекс быстро пересобирается из cached embeddings.

Порядок ручного перезапуска:

1. Убедитесь, что нужная категория уже есть в `Данные` -> `Куб`.
2. Откройте `Данные` -> `ML-дедуп`.
3. Укажите локальный путь модели, если веса лежат на этой машине.
4. Отметьте eligible-категории. В списке показывается одна бизнес-категория, даже если в кубе она пришла несколькими исходными `category_key` по разным маркетплейсам: например, одно `Кокосовое масло` может включать Ozon, WB и Яндекс.Маркет.
5. Нажмите `Запустить`.

В блоке `Запуски` верхняя плашка `Текущий запуск` показывает последний run без горизонтального скролла: статус, процент, текущий этап, таймер выполнения, SKU-node, FAISS-кандидаты, проскоренные пары и группы. Ниже остаётся таблица запусков со статусом, прогрессом по этапам, cache status (`identity hit`, `cache hit`, `cache partial`, `cache rebuilt`, `cache skipped`), временем выполнения, количеством SKU-node, FAISS-кандидатов, модельных пар и групп. Пока run выполняется, плашка и таблица обновляются автоматически. На этапе cross-encoder scoring прогресс показывает, сколько пар уже проскорено из общего числа кандидатов и сколько взято из score-cache. Повторный запуск той же категории не создаёт пачку одинаковых failed-строк: активный run переиспользуется, а старый неуспешный run той же категории заменяется новой попыткой. Успешный повторный run заменяет строки этой бизнес-категории в `mpstats_products_dedup`, чтобы браузер и CSV не копили старые результаты. Для успешного запуска можно открыть артефакты `groups` и `edges`.

Блок `Браузер SKU` показывает готовую таблицу `mpstats_products_dedup`:

- режим `Основная` выводит общий базовый товар на первом уровне, а на втором уровне — разные фасовки внутри этой ML-группы. Фасовка включает объём и наборность: например, 180 мл, 450 мл, 180 мл 2 шт и 450 мл 3 шт будут разными строками второго уровня. Исходные SKU-дубли внутри фасовки в этом режиме не показываются;
- режим `Дубли` оставляет прежний подробный вид: строка канона фасовки на первом уровне и входящие SKU-node ниже. Разные фасовки остаются разными строками первого уровня;
- в режиме `Дубли` у строк исходных SKU есть кнопка `Убрать`: она вынимает выбранный SKU из текущей family, делает его отдельным singleton и сразу пересобирает `mpstats_products_dedup`. Исходная строка в кубе не удаляется. Правка сохраняется как ML-override и применяется в следующих run той же бизнес-категории, поэтому модель/identity-cache не склеят этот SKU обратно автоматически;
- в режиме `Основная` название базового товара дополнительно чистится от простых хвостов вида `180 мл`, `2 шт` или `набор: 3 штуки`, чтобы разные фасовки не выглядели как разные базовые товары;
- канон фасовки показывается один раз на ML-группу фасовки, даже если входящие SKU пришли из нескольких исходных category-key;
- режим `Каноны` выводит только верхний уровень с нормализованным названием;
- поиск работает по SKU, бренду, артикулу, категории и маркетплейсу.
- ширину колонок можно менять перетаскиванием правого края заголовка.

CSV-выгрузки результата ML-дедупа находятся в `Данные` -> `Выгрузка`, в блоке `ML-дедуп CSV`. Кнопка `CSV 2 уровня` выгружает каноны вместе с входящими SKU, а `CSV каноны` выгружает только первый уровень с нормализованными названиями. Файлы сохраняются в `data/projects/<project>/exports/`.

После успешного run вкладка `Данные` -> `Выгрузка` получает режим
`Дедупликация ON/OFF`. В режиме `OFF` плоская выгрузка строится из исходной
`mpstats_products`: без ML-колонок и без замены названий. В режиме `ON`
выгрузка всё равно берёт строки из исходной таблицы и сохраняет их количество,
но в колонке `SKU` для найденных дублей подставляет нормализованное название
базового товара, например `Кокосовое масло` вместо вариантов с объёмом,
набором и маркетинговым хвостом. Строки фактов не схлопываются.

## 17. Раздел `Данные` -> `Отчёты`

Эта вкладка нужна для больших категорий и регулярных аналитических таблиц. Она строит агрегированные отчёты из куба в локальной DuckDB и отдаёт в Excel уже подготовленную таблицу.

Сырые строки из `mpstats_products` в интерфейс целиком не загружаются. Приложение считает отчёт SQL-запросом и показывает только первые строки предпросмотра.

Сверху видно:

- сколько категорий есть в кубе;
- сколько из них помечены как тяжёлые;
- сколько категорий выбрано для отчёта;
- текущий порог тяжёлого среза.

В списке `Тяжёлые категории` показаны категории, по которым лучше не открывать raw-данные в Excel. Для них доступны отчётные таблицы:

- `Категория по месяцам`;
- `Бренды по месяцам`;
- `Классификация по месяцам`;
- `Топ SKU`.

Порядок работы:

1. Откройте `Данные` -> `Отчёты`.
2. Выберите тип отчёта.
3. При необходимости сузьте период и категории.
4. Нажмите `Предпросмотр`.
5. Нажмите `XLSX` или `CSV`.

Если папку не менять, отчёты сохраняются в:

```text
data/projects/<название проекта>/reports/
```

После сборки в `Куб` обновляется время последнего отчёта для выбранных категорий.

## 18. Раздел `Данные` -> `Выгрузка`

Эта вкладка делает итоговые XLSX- или CSV-файлы из данных, уже сохранённых в локальной БД.

Сверху выбираются параметры:

- период;
- категории;
- нужные колонки;
- папка для результата;
- формат `XLSX` или `CSV`;
- режим `Дедупликация ON/OFF`;
- режим `Разными файлами по категориям`.

### Шаблоны выгрузки

В блоке `Шаблон` можно сохранить текущие настройки выгрузки: период, категории, колонки, фильтры строк, сортировку, папку, формат, режим дедупликации и режим разбиения по категориям.

После сохранения шаблон появляется списком в этом же блоке:

- `Применить` подставляет настройки шаблона в форму выгрузки;
- `XLSX` или `CSV` сразу запускает выгрузку по шаблону из уже сохранённого куба;
- `Удалить` убирает шаблон.

Шаблон не скачивает MPStats заново. Он работает только с данными, которые уже есть в кубе текущего проекта.

Если папку не менять, файлы сохраняются в:

```text
data/projects/<название проекта>/exports/
```

Если указать свою папку, приложение автоматически добавит в неё подпапку текущего проекта. Например, для проекта `unit` путь `~/Reports/MPStats` превратится в `~/Reports/MPStats/unit`.

### ML-дедуп CSV

Блок `ML-дедуп CSV` находится в этой же вкладке. Он работает с уже готовой таблицей `mpstats_products_dedup`, которая появляется после успешного ML-дедуп run.

- `CSV 2 уровня` выгружает каноническую строку и входящие в неё SKU-node;
- `CSV каноны` выгружает только первый уровень с нормализованными названиями;
- выпадающий список категории можно оставить в режиме `Все eligible-категории` или выбрать одну категорию.

Эти кнопки не запускают ML-дедуп заново. Если результата ещё нет, сначала откройте `Данные` -> `ML-дедуп` и запустите нужные eligible-категории.

### Предпросмотр

Кнопка `Предпросмотр` показывает первые строки будущей выгрузки. В таблице можно:

- фильтровать значения по колонкам;
- сортировать по колонке;
- менять ширину колонок перетягиванием правого края заголовка;
- снять лишние колонки;
- убрать отдельные строки из текущей выгрузки.

В блоке `Фильтры строк` задаются фильтры, которые реально попадут в текущую выгрузку. Для числовых колонок можно выбрать условия `>`, `>=`, `<`, `<=`; например `Продажи, шт` `>` `0`, чтобы убрать строки без продаж.

Кнопка `убрать` не удаляет строку из БД. Она только исключает её из текущей спецификации выгрузки. Кнопка `Вернуть исключённые` очищает этот список.

После предпросмотра приложение показывает `Состав выгрузки`: конкретные сочетания `период / категория / маркетплейс / количество строк`. Этот список помогает увидеть, какие месячные срезы и категории попадут в итоговый файл.

### Экспорт XLSX/CSV

Переключатель `Дедупликация ON/OFF` относится к обычной плоской выгрузке:

- `OFF` — выгружается исходный `SKU` из куба, без ML-колонок;
- `ON` — количество строк остаётся тем же, но `SKU` заменяется на
  нормализованное название базового товара из последнего успешного ML-дедуп
  run, если для строки найдена группа. Вес, объём и мультипак остаются в
  отдельных колонках куба. Если группы нет, остаётся исходный `SKU`.

Переключатель `XLSX / CSV` выбирает формат результата. Кнопка выгрузки показывает выбранный формат.

Для `XLSX` приложение создаёт простую плоскую таблицу с одной строкой заголовков. В файле нет стилей, заморозки шапки, автофильтров, формул и дополнительных листов: такой формат быстрее строится и удобен как источник для Excel-сводников.

`CSV` приложение создаёт с разделителем `;` и кодировкой `utf-8-sig`, чтобы файл нормально открывался в Excel. В CSV дробные числа выгружаются с десятичной запятой для русской локали Excel и Power Query. Текстовые измерения `Дата`, `SKU`, `продавец`, `категория`, `бренд`, `год`, `месяц`, `подкатегория` и `тип` не форматируются, поэтому точки в таких значениях сохраняются. CSV- и XLSX-выгрузки строятся из одного SQL-запроса напрямую из локальной DuckDB, без промежуточной загрузки всех строк в pandas.

Для Excel-сводников числовые колонки вроде `Продажи, шт`, `Выручка, руб`, `Вес, кг`, `Вес, кг (ед.)`, `Объем, кг`, `Средняя цена, руб`, `Цена за кг` и похожие поля выгружаются как числа, а дата-колонки — как даты, если значение можно корректно привести. Сама таблица в БД при этом не меняется.

Если в форме не выбрана сортировка, файл сохраняется в естественном порядке БД; чтобы получить конкретный порядок строк, выберите колонку сортировки перед выгрузкой.

Если выключен режим `Разными файлами по категориям`, приложение делает общий файл по выбранным категориям. Если режим включён, для каждой категории/маркетплейса создаётся отдельный файл.

Excel ограничивает лист размером 1 048 576 строк. Приложение оставляет одну строку под заголовок, поэтому один XLSX-файл может содержать до 1 048 575 строк данных.

Если XLSX-выгрузка превышает этот лимит, приложение не пытается создать один большой XLSX и показывает ошибку `XLSX row limit exceeded, use CSV`. В таком случае выберите формат `CSV` или сузьте период/категории. Для больших аналитических таблиц также можно использовать `Данные` -> `Отчёты`.

Если файлов получается больше 10, приложение попросит подтвердить большую выгрузку.

Во время сборки появляется прогресс-бар: он показывает текущий шаг, процент, количество записанных строк и количество готовых файлов.

## 21. Типовые проблемы и что делать

### Cookie устарел

Признаки:

- скачивание падает;
- MPStats отвечает ошибкой доступа;
- отчёты не создаются.

Что сделать:

1. Откройте MPStats в браузере.
2. Обновите cookie.
3. Вставьте новый cookie в приложение.
4. Нажмите `Сохранить настройки`.
5. Нажмите `Повторить ошибки`.

### Пустой API token для предмета

Признаки:

- задача `По предмету` падает с сообщением про пустой `MPStats API token`;
- обычные строки `По категории` при этом могут продолжать работать по cookie.

Что сделать:

1. Получите актуальный token MPStats Analytics API.
2. Вставьте его в поле `MPStats API token`.
3. Нажмите `Сохранить настройки`.
4. Нажмите `Повторить ошибки`.

### Категория не появилась во вкладке `Категории`

Проверьте:

- строка сохранена в редакторе `Справочник`;
- включена `Активна в приложении`;
- указан маркетплейс;
- заполнен путь или ID предмета;
- период `От / До` не исключает выбранный месяц.

После правок нажмите `Сохранить CSV`, затем `Обновить справочник`.
Если CSV менялся вручную вне приложения, достаточно открыть или обновить раздел `Категории`: приложение перечитает общий локальный справочник.

### В плане меньше задач, чем ожидалось

Обычно причина одна из следующих:

- у части строк справочника выключена активность;
- период строки не пересекается с выбранным диапазоном;
- выбраны не все пути внутри группы;
- часть путей уже сохранена в БД и будет пропущена при запуске.

### Задача получила `нет данных`

Это значит, что для выбранного пути, фильтра и месяца MPStats вернул пустой результат. Проверьте путь, фильтр и период в MPStats.

### Ошибка на обработке

Чаще всего причина в неожиданном формате CSV или отсутствии нужных колонок в выгрузке. Откройте raw-файл через `Данные` -> `Файлы` и проверьте, что MPStats действительно отдал товарные колонки.

### Вес считается неправильно

Проверьте название товара. Если формат веса новый или нестандартный, строка может попасть в аномалии.

Для отчёта можно:

- проверить `Вес, кг` и `Вес, кг (ед.)`;
- посмотреть `Вес причина`;
- исправить правило парсинга в проекте, если таких товаров много;
- временно поправить итоговый файл вручную, если это единичный случай.

### Классификация не сработала

Проверьте правило:

- оно активно;
- категория совпадает или стоит `*`;
- условие ищет в правильной колонке;
- текст поиска действительно есть в товаре;
- режим `заполнить пустое` не мешает перезаписать уже заполненную колонку;
- порядок правил не приводит к тому, что более раннее правило заполняет колонку раньше.

Если нужно принудительно исправить уже заполненное значение, используйте режим `перезаписать`.

### В БД не появились новые строки

Проверьте:

- задача дошла до статуса `в БД`;
- выбран правильный проект;
- срез уже мог быть сохранён раньше;
- если нужно заменить старый срез, включите `Перезаписывать БД` и повторите задачу.

### В выгрузке нет строк

Проверьте:

- выбран правильный проект;
- данные уже сохранены в `Данные` -> `Куб`;
- выбранный период пересекается с сохранёнными месяцами;
- выбрана хотя бы одна категория;
- фильтры по колонкам не исключили все строки.

## 22. Research-only разметка SKU-дублей

Этот сценарий не относится к основному web-приложению и нужен только для
исследовательских gold-set по SKU-дедупликации. Сейчас поддержаны три
category-run:

- `sauces` — проект `Соусы_тест`, категории `Соусы` / `Соус`;
- `coconut_oil` — проект `кокос_тест`, категория `Кокосовое масло`;
- `soap` — проект `мыло_тест`, категория `Мыло`.

Обычные параметры research-ноутбуков теперь задаются прямо в первых
code-ячейках через `MY_*`. В `.env` оставляйте только секреты и машинные
служебные настройки, которые не хочется хранить в notebook:

```env
POLZA_API_KEY=...
POLZA_BASE_URL=https://polza.ai/api/v1
DEDUP_MODEL_CACHE_DIR=research/dedup/models
DEDUP_MODEL_LOCAL_ONLY=0
```

Research helpers автоматически читают `.env` при импорте `research.dedup`.
Они по-прежнему используют `POLZA_*`, `HF_TOKEN`,
`DEDUP_MODEL_CACHE_DIR`, `DEDUP_MODEL_LOCAL_ONLY` и настройки Telegram-бота.
Category-run, DuckDB path, размеры выборок, FAISS/reranker-параметры и
пороговые настройки меняйте в notebook, не в `.env`.

Если `MY_CATEGORY_RUN` не менять, используется `sauces`. Для `sauces`
сохранены старые пути `research/dedup/data/*_sauces.csv` и
`artifacts/reports/binary_threshold_*.csv`. Для новых категорий файлы
изолированы и не перетирают sauce-артефакты:
`research/dedup/data/coconut_oil/`, `artifacts/reports/coconut_oil/`,
`research/dedup/data/soap/`, `artifacts/reports/soap/`.

Перед выполнением research-ноутбуков установите зависимости для embedding
blocking:

```bash
python3 -m pip install -r requirements-research.txt
```

Активный research-flow `notebooks/00_eda.ipynb` ->
`notebooks/05_grouped_sku_demo.ipynb` оформлен как единое исследование:
в начале каждого notebook есть оглавление, краткое введение, первая code-ячейка
с пользовательскими `MY_*` настройками и финальный блок выводов. Обычные
параметры запуска меняйте в первой code-ячейке, а `.env` оставляйте для
секретов, model cache и пути к DuckDB. Outputs в git не хранятся: после
изменения параметров запускайте нужный notebook сверху вниз.

В `notebooks/00_eda.ipynb` есть опциональный первый EDA-блок для почтового
архива PST/OST: он через `pypff`/`libpff` считает письма с MPStats/ecom/
marketplace-ключевыми словами, показывает месячную динамику, долю тем
пирогом, топ доменов-отправителей и сохраняет агрегаты в
`artifacts/reports/mail_archive_eda/`. Для запуска на машине с архивом
установите `sudo apt install python3-pypff pff-tools`, задайте
`MY_MAIL_ARCHIVE_PATH` и включите `MY_RUN_MAIL_ARCHIVE_EDA = True` в первой
code-ячейке. Тело писем не экспортируется в CSV: оно используется только для
поиска ключевых слов.

`notebooks/01_candidate_generation.ipynb` строит большой пул пар-кандидатов.
Основной слой — dense embeddings и FAISS top-k: FAISS отвечает за поиск
похожих соседей, но теперь не является единственным источником обучающих пар.
Чтобы дорогая разметка не зависела только от текущего `MY_FAISS_TOP_K`, candidate
CSV дополнительно получает supplemental пары: lexical overlap,
same-brand/same-pack controls, cross-marketplace random и random controls.
Затем `notebooks/02_labeling_dataset.ipynb` выбирает из этого пула CSV для
ручной разметки: часть cross-marketplace, часть hard negatives, часть pack
variants, часть high/medium/low similarity. По умолчанию notebook 01 берёт
`MY_FAISS_TOP_K = 30`; для локального E5 embedding используется `query:` prefix,
потому что товары сравниваются друг с другом как symmetric similarity, а не
как поисковый запрос против документа.
Score-страты в `02` по умолчанию считаются относительно текущего списка
FAISS-кандидатов: top 25% score идут в `high_similarity`, bottom 25% — в
`random_easy_negative`, середина — в `medium_similarity`. Это важно, потому
что cosine scores зависят от embedding-модели и категории. Старый режим
абсолютных порогов можно включить через
`MY_LABELING_SCORE_STRATIFICATION = "absolute"`; доли quantile-режима меняются
через `MY_LABELING_HIGH_TOP_SHARE` и `MY_LABELING_EASY_BOTTOM_SHARE`.
Пары, где оба бренда заполнены и бренды разные, ограничены отдельным лимитом:
по умолчанию `MY_LABELING_MAX_DIFFERENT_BRAND_SHARE = 0.20`, то есть не
больше 20% итогового CSV. Уже размеченные строки не удаляются при
перегенерации: `02` читает существующий `LABELING_PATH`, сохраняет заполненные
`label`-строки, пишет рядом backup `*_preserved_labels.csv` и добирает только
незаполненный остаток.
Для параллельной разметки можно задавать разным людям разные random-срезы
через `MY_LABELING_BATCH_ID`, например `exoldoff` и `friend`. Это меняет
seed выборки, но оставляет воспроизводимость: один и тот же batch id даёт тот
же случайный срез при тех же входных candidates.
Для быстрого benchmark старый сценарий остаётся прежним: один
category-run в `MY_CATEGORY_RUNS` и около 400 строк. Для датасета под
fine-tuning reranker
сначала перегенерируйте `01_candidate_generation.ipynb` для каждой категории,
чтобы `candidates_<suffix>.csv` уже содержал широкий training pool. Затем
собирайте один CSV по всем трём категориям, поменяв первую code-ячейку `02`:

```python
MY_CATEGORY_RUNS = ["sauces", "coconut_oil", "soap"]
MY_LABELING_TARGET_SIZE = 3000
MY_LABELING_SCORE_STRATIFICATION = "quantile"
MY_LABELING_MAX_DIFFERENT_BRAND_SHARE = 0.20
MY_LABELING_PRESERVE_EXISTING_LABELS = True
```

Рекомендуемый набор в первой code-ячейке `01` для первого fine-tuning
labeling set:

```python
MY_FAISS_TOP_K = 30
MY_FAISS_SUBCATEGORY_BLOCKING = True
MY_FAISS_GLOBAL_SAFETY_TOP_K = 5
MY_FAISS_UNKNOWN_SUBCATEGORY_TOP_K = 30
MY_FAISS_MAX_CANDIDATES = 1000000

MY_SUPPLEMENTAL_LEXICAL_PAIRS = 8000
MY_SUPPLEMENTAL_SAME_BRAND_PACK_PAIRS = 6000
MY_SUPPLEMENTAL_CROSS_MARKETPLACE_RANDOM_PAIRS = 3000

```

При таком запуске notebook делит размер примерно поровну между категориями
и добавляет в CSV колонки `category_run`, `category_name`, `project_name`.
Если нужно оставить больше FAISS-соседей вместе с supplemental парами,
перед запуском `01` можно увеличить `MY_FAISS_MAX_CANDIDATES`, например до
`120000`.
Если в срезе есть заполненная колонка `Подкатегория`, FAISS по умолчанию
ищет основной top-k внутри одной подкатегории. Это сокращает пул кандидатов
для `Мыло` и `Соусы`: `жидкое` не конкурирует с `твердое`, а `соевые` не
конкурируют с `кетчуп`. Второй подуровень для соусов не используется.
Если `Подкатегория` отсутствует или полностью пустая, как у текущего среза
`Кокосовое масло`, notebook автоматически откатывается в старый full-global
FAISS-поиск без ограничения по подкатегории.
Для защиты от ошибок классификации остаётся маленький full-global safety-net,
а строки с пустой `Подкатегория` тоже ищут соседей по всему срезу. Настройки:
`MY_FAISS_SUBCATEGORY_BLOCKING = False` отключает режим,
`MY_FAISS_GLOBAL_SAFETY_TOP_K` задаёт размер safety-net,
`MY_FAISS_UNKNOWN_SUBCATEGORY_TOP_K` задаёт top-k для строк с пустой
подкатегорией.
Перед расчётом embeddings строки с одинаковым title и одинаковым `Бренд`
автоматически схлопываются в один research-record. Пустой `Бренд` считается
отдельным значением, поэтому одинаковые безбрендовые SKU тоже схлопываются.
Это убирает очевидные exact-title дубли из FAISS-соседей; исходные артикулы
остаются в метаданных `source_raw_record_ids` / `source_skus`.
После FAISS-блока notebook показывает несколько anchor-SKU и их ближайших
соседей из текущего списка кандидатов. Количество групп, размер группы и режим выбора
можно менять через `MY_NEIGHBOR_GROUP_COUNT`,
`MY_NEIGHBOR_GROUP_SIZE` и `MY_NEIGHBOR_GROUP_SAMPLE_MODE`.

Для запуска новой категории поменяйте `MY_CATEGORY_RUN` в `00`, `01` и `05`.
В `02`, `03` и `04` используется список `MY_CATEGORY_RUNS`: для одного run
оставьте один элемент, для общего multi-category сценария оставьте
`["sauces", "coconut_oil", "soap"]`.

Все research-ноутбуки фильтруют DuckDB не только по `Категория`, но и по
`__project_name`, чтобы `Мыло` из проекта `мыло_тест` не смешивалось с другими
проектами той же категории.

По умолчанию он открывает

Можно также передать любой CSV первым аргументом.

На экране аннотатор компактно показывает пару A/B: title, SKU, marketplace,

Классы разметки теперь бинарные: `exact_duplicate` означает тот же базовый

- `DEDUP_TELEGRAM_ASSIGNMENT_MODE=overlap` — строку могут разметить несколько

- `DEDUP_TELEGRAM_ASSIGNMENT_TTL_HOURS=24` — через сколько часов неразмеченные

- `DEDUP_TELEGRAM_DISCUSSION_CHAT_ID=-100...` — общий чат, куда уходят пары

- `DEDUP_TELEGRAM_LEADERBOARD_CHAT_ID=-100...` — чат, где бот держит
  закреплённое сообщение с топом команд. Если не задан, используется

- `DEDUP_TELEGRAM_COMBO_TIMEOUT_SECONDS=300` — окно командного комбо: после
  каждого финального ответа у команды есть 5 минут, чтобы дать следующий
  финальный ответ и продлить серию.

Если `DEDUP_TELEGRAM_STATE_PATH` не задан, state хранится рядом с CSV:
`<labeling_csv>.telegram_state.sqlite`. Файлы SQLite и WAL/SHM игнорируются
git.

Команды бота:

- `/start <пароль>` — войти;
- `/help` — подсказка;
- `/menu` — показать команды;
- `/next` — получить следующую пару;
- `/me` — личная статистика;
- `/team <название>` — вступить в команду или создать новую;
- `/teams` — показать топ команд с личным вкладом участников;
- `/players` — показать топ игроков по личным финальным ответам;
- `/achievements` — показать свои личные ачивки и ачивки текущей команды с
  датой и временем получения;
- `/revive` — восстановить лучшую потерянную серию своей команды;
- `/stats` — общий прогресс и статистика по пользователям;
- `/release` — освободить свои неразмеченные пары;
- `/logout` — выйти и освободить активные пары.

При запуске бот регистрирует эти команды в Telegram, поэтому они доступны в
синей кнопке меню команд рядом со строкой ввода.

Кнопки под парой:

- `Дубль` — `exact_duplicate`;
- `Разные` — `different_product`;
- `Не уверен` — `uncertain`;
- `Назад` — вернуться к предыдущей паре из своей истории;
- `Дальше` — показать следующую пару из текущего батча или добрать новый
  батч.

После выбора решения бот сохраняет голос, отмечает выбранный вариант галочкой
`✓` и автоматически перелистывает к следующей паре. Если вернуться кнопкой
`Назад`, уже сохранённое решение видно в сообщении и на кнопке.
Чтобы изменить решение, нажмите другую кнопку разметки на этой же паре: в
unique-режиме бот обновит и SQLite-state, и значение `label` в CSV.
Кнопка `Дальше` и автоперелистывание после ответа пропускают уже заполненные
строки из CSV, даже если они остались в вашей старой истории или были решены
кем-то ещё. Если пользователь нажал кнопку на устаревшем сообщении, а строка
уже закрыта, бот не перезаписывает CSV и пытается сразу показать следующую
актуальную пару.

Сообщение с парой форматируется для быстрого чтения: структурные поля
выделены жирным, значения `SKU` показаны моноширинным шрифтом, а названия и
сигналы безопасно экранируются для Telegram HTML. Служебная информация
показывается над товарами, включая подкатегории и сигналы. Внизу сообщения
остаются блоки `SKU A` и `SKU B`: id SKU, маркетплейс, бренд, название и
фасовка идут отдельными строками, а вместо текстовых названий атрибутов
используются эмодзи-маркеры.

На контрольных точках `100`, `300`, `500`, `1000`, `1500`, `2000`, `2500`,
`3000` заполненных строк бот отправляет неформальное мотивационное сообщение
всем авторизованным пользователям. Если настроен
`DEDUP_TELEGRAM_DISCUSSION_CHAT_ID`, такое же сообщение уходит и в общий чат.
Факт отправки каждого рубежа хранится в SQLite-state, поэтому после рестарта
бот не должен дублировать уже объявленные контрольные точки.

Игровой зачёт включен всегда. Личный счёт в `/players` растёт за каждый
финальный ответ пользователя, даже если он пока без команды. Командные очки
начисляются только пользователям, которые вступили в команду через
`/team <название>`. Название создаёт команду, если её ещё нет, или присоединяет
пользователя к существующей команде с таким же названием. Командный счёт —
сумма финально решённых пар участников; личный вклад виден в `/teams`,
`/stats` и `/me`. В overlap-режиме очки начисляются после консенсуса, то есть
черновые голоса не разгоняют игру раньше записи в CSV.

Ачивки выдаются один раз и сохраняются в SQLite-state. Сейчас есть личные
ачивки за пороги финальных ответов (`1`, `10`, `25`, `50`, `100`), командные
ачивки за командный счёт (`10`, `25`, `50`, `100`, `250`) и отдельные
комбо-ачивки (`x3`, `x5`, `x10`, `x20`). Новая ачивка рассылается как
игровое сообщение только в групповые чаты, а текущий список доступен через
`/achievements`: бот показывает личные и командные ачивки вместе с временем
получения в МСК.

Если задан `DEDUP_TELEGRAM_LEADERBOARD_CHAT_ID` или общий discussion chat,
бот создаёт и дальше редактирует одно сообщение с топом команд. Он пытается
закрепить это сообщение через Telegram API; для настоящего закрепа бот должен
быть админом чата с правом pin messages. Если прав нет, сообщение всё равно
будет создано и обновляться, но Telegram его не закрепит.

Когда команда обгоняет текущего лидера, бот рассылает отдельное сообщение
всем авторизованным пользователям, в discussion chat и в leaderboard chat.
Комбо работает по таймеру: после финального ответа команды запускается окно
на `DEDUP_TELEGRAM_COMBO_TIMEOUT_SECONDS`; если команда успевает дать ещё
ответ, серия растёт. На хороших сериях (`x3`, `x5`, `x10`, дальше крупные
пороги) бот пишет отдельный хайп-сигнал. Если окно истекло без нового
финального ответа, комбо сбрасывается и бот отправляет сообщение о сбросе.
Все сообщения про комбо, включая сброс, тоже отправляются только в групповые
чаты `DEDUP_TELEGRAM_DISCUSSION_CHAT_ID` / `DEDUP_TELEGRAM_LEADERBOARD_CHAT_ID`,
без личной рассылки игрокам.

Под сообщением о сбросе комбо появляется inline-кнопка
`Восстановить (N)`, где `N` — сколько возрождений осталось у команды.
Возродить серию может только участник этой команды. После нажатия старый
combo-счёт возвращается, снова запускается 5-минутное окно, а лимит
уменьшается на 1. Если команда уже успела набрать новую живую серию, бот
оставит максимум из живой и восстанавливаемой серии, поэтому revive не
откатывает счёт вниз. Если сообщение со сбросом уже ушло вверх или кнопка
недоступна, участник команды может вызвать `/revive`: бот найдёт максимальную
неиспользованную потерянную серию этой команды и восстановит её по тому же
правилу максимума. Если таймер уже истёк, но событие сброса ещё не успело
записаться в state-файл, `/revive` сначала сам перенесёт эту серию в
потерянные, а затем восстановит. Всего у каждой команды 5 возрождений на
весь state-файл.

Если в терминале иногда появляется `telegram.error.TimedOut` или warning про
сетевой timeout при нажатии inline-кнопки, это означает, что Telegram API не
успел ответить на короткий callback-запрос. Бот продолжает обработку, а
финальные ответы, ачивки и CSV-state не должны теряться. При остановке через
`Ctrl+C` бот также отменяет фоновые combo-таймеры, чтобы не оставлять в
терминале шум вида `Task was destroyed but it is pending`.

Если настроен `DEDUP_TELEGRAM_DISCUSSION_CHAT_ID`, кнопка `Не уверен` не
пишет `uncertain` в CSV сразу. Вместо этого бот отправляет пару в общий чат
с кнопками `Дубль`, `Разные`, `Не уверен`. Авторизованные пользователи могут
голосовать прямо из общего чата. Когда набирается консенсус по
`DEDUP_TELEGRAM_OVERLAP_VOTES`, итоговая метка записывается в CSV, а кнопки
под обсуждением снимаются. Сообщение в общем чате показывает текущие голоса:
кто и какой вариант выбрал на данный момент. Если за 30 минут консенсус не
собрался, бот автоматически закрывает обсуждение как скип и записывает в CSV
`uncertain`. Если общий чат не настроен, `Не уверен` работает как обычная
метка и записывает `uncertain` по правилам текущего режима.

В overlap-режиме, если голоса разошлись, бот не пишет итог в CSV и помечает
строку как `conflict` в SQLite-state. Такие конфликты видны в `/stats` и
разбираются вручную.

По умолчанию `03_matching_comparison.ipynb` читает frozen split:

```text
research/dedup/data/training/dedup_pairs_final_pair_stratified_split.csv
```

Это all-pairs benchmark на 2465 размеченных пар. Если нужен strict no-leak
split, который использовался для обучения текущей BGE, поменяйте путь в

MY_EVAL_DATA_PATH = "research/dedup/data/training/dedup_pairs_final_split.csv"

Notebook сохраняет готовую колонку `split`: `train` можно скорить для
диагностики, но threshold выбирается только на `dev`, а финальные метрики
смотрятся на `test`. Правило простое:

```python
predicted_binary = 1 if score >= threshold_same else 0
```

`same_base_product = 1` для `exact_duplicate` и legacy
`same_product_different_pack`; `same_base_product = 0` для
`different_product`. Manual review, LLM-review и triage на этом этапе не
запускаются.

Для каждого method считаются стратегии:

- `threshold_max_f1` — максимальный обычный F1 на dev;
- `threshold_cost_sensitive` — минимум
  `FP_COST * false_merge_count + FN_COST * false_split_count`;
- `threshold_max_weighted_f1` и `threshold_weighted_cost`, если доступны
  объёмы продаж.

Notebook сравнивает текущие методы:
`rule_based_fuzzy`, `bi_encoder_zero_shot`, `cross_encoder_zero_shot` и
reranker-модели из общего benchmark.
Cross-encoder — более внимательная проверка пары, но первый запуск может
скачивать модель из Hugging Face. Если нужно временно пропустить этот блок,
поставьте в первой code-ячейке `MY_RUN_CROSS_ENCODER = False`.

После прогона `03` сохраняет compact-отчёты в `artifacts/reports/fine_tuning/`,
если `MY_REPORTS_DIR` не переопределён.

- `binary_threshold_summary.csv` — одна строка на
  `method + split + threshold_strategy`;
- `binary_threshold_predictions.csv` — score, true label, predicted label,
  `false_merge`, `false_split`, `pair_weight` и контекст пары;
- `binary_threshold_by_volume_bucket.csv` — появляется только если доступны
  weighted-метрики по объёму продаж.

Raw predictions и старые `matching_*` CSV этот benchmark не перезаписывает.

В конце `03_matching_comparison.ipynb` есть общий benchmark всех текущих
matching-моделей на одном frozen score scope:

- `rule_based_fuzzy`;
- `bi_encoder_zero_shot`;
- `cross_encoder_zero_shot`;
- `reranker_bge_v2_m3`;
- `reranker_qwen3_4b`;
- `reranker_jina_v3`.
- `ft_bge_reranker_v2_m3` — fine-tuned BGE из локального server backup,
  если путь к модели существует.

Главный файл для сравнения методов — теперь
`binary_threshold_summary.csv` в reports-папке текущего run. Test split нельзя
использовать ни для выбора threshold, ни для выбора bucket cutoffs, ни для
выбора модели; он нужен только для финальной проверки.

В конце notebook также строятся inline-графики: сравнение качества и стоимости
ошибок на test, false merge/false split по стратегиям, распределения score с
линиями выбранных thresholds и bucket-разбор по объёму продаж, если weighted
метрики доступны.

Запуск zero-shot rerankers обычный: откройте notebook и поменяйте первую
code-ячейку с `MY_*` настройками.

Главные настройки:

```python
MY_RERANKER_MODELS = [
    "bge_m3",
    # "qwen3_4b",
    # "jina_v3",
    # "cross-encoder/ms-marco-MiniLM-L6-v2",
]
MY_RERANKER_MAX_PAIRS = 0  # весь выбранный frozen score scope
MY_CUSTOM_RERANKER_BACKEND = "cross_encoder"
```

Fine-tuned модели настраиваются там же, в первой code-ячейке:

```python
MY_FINE_TUNED_MODELS = [
    {
        "enabled": True,
        "method": "ft_bge_reranker_v2_m3",
        "model_path": "/Users/exoldoff/Desktop/mpstats_server_backup_20260630_041745/artifacts/models/dedup/bge_reranker_v2_m3_v1/final",
        "score_column": "ft_bge_reranker_v2_m3",
        "activation": "sigmoid",
    },
]
```

Для новых fine-tuned моделей можно добавить ещё один dict с `model_path`.
Если score уже посчитан training script-ом, вместо `model_path` укажите
`score_path` и `score_column`: notebook подхватит CSV без повторного inference.

Cost-параметры и weighted-join тоже задаются в первой code-ячейке:

```python
MY_FP_COST = 5
MY_FN_COST = 1
MY_ENABLE_SALES_VOLUME_JOIN = True
```

Модели можно писать короткими alias-ами из registry (`bge_m3`, `qwen3_4b`,
`jina_v3`) или полными Hugging Face model ids
(`BAAI/bge-reranker-v2-m3`, `Qwen/Qwen3-Reranker-4B`).
Для Qwen reranker используется общий SKU-prompt без привязки к одной
категории: он подходит для `sauces`, `coconut_oil` и `soap`.

Для первого спокойного запуска оставьте `MY_RERANKER_MAX_PAIRS = 120`.
В этом случае все методы, включая старые baseline, сравниваются на тех же
120 парах. Для финального выбора лучшего решения поставьте
`MY_RERANKER_MAX_PAIRS = 0`.

Если вписываете свой model id, которого ещё нет в registry, оставьте
`MY_CUSTOM_RERANKER_BACKEND = "cross_encoder"` для обычных
`sentence_transformers.CrossEncoder` моделей. Для Jina-like моделей с
методом `.rerank` используйте `"transformers_auto_model"`.

Можно запускать только одну модель:

```python
MY_RERANKER_MODELS = ["bge_m3"]
MY_RERANKER_MODELS = ["qwen3_4b"]
MY_RERANKER_MODELS = ["jina_v3"]
```

Jina v3 удобна для эксперимента, но перед production-использованием нужно
отдельно проверить лицензионные условия.

Если в таблице статусов все reranker-модели падают с ошибкой про
`huggingface_hub` или `logging`, обновите research-зависимости в том Python,
который выбран как Jupyter kernel, и перезапустите kernel:

```bash
python3 -m pip install -U -r requirements-research.txt
```

После `03` запустите `04_fusion_pack_grouping.ipynb`. Он не запускает модели
заново: берёт `binary_threshold_summary.csv` и
`binary_threshold_predictions.csv`, выбирает fusion-run только по `dev` и
строит два уровня групп:

- `family` — один базовый товар, даже если отличается вес или multipack;
- `pack` — конкретная фасовка внутри family по `Вес, кг (ед.)`, `Вес, кг` и
  `multipack_count`.

Для текущего frozen/fine-tuning benchmark `04` можно запускать один раз на все
три категории. По умолчанию:

- `MY_CATEGORY_RUNS = ["sauces", "coconut_oil", "soap"]`;
- `MY_REPORTS_DIR_OVERRIDE = "artifacts/reports/fine_tuning"` — общий reports
  folder из `03`;
- `MY_EVAL_DATA_PATH` указывает на frozen split и нужен, если predictions CSV
  не содержит `category_run`.

Notebook сам восстановит `category_run` по `benchmark_pair_key`, разложит пары
по категориям и сохранит отдельные `fusion_*` CSV в стандартные пути каждого
run. Если нужно вернуться к старому per-category режиму, поставьте
`MY_REPORTS_DIR_OVERRIDE = None`.

По умолчанию `04` выбирает бизнес-взвешенный режим: сначала
`threshold_weighted_cost`, где ошибки на товарах с большими продажами стоят
дороже. Если в outputs из `03` нет weighted-строк, notebook откатывается на
`threshold_cost_sensitive`. Если нужно вручную зафиксировать вариант, в блоке
`Пути и настройки` меняйте `MY_*` значения прямо в notebook:

- `MY_FUSION_METHOD = None` — выбрать method автоматически по `dev`.
  Можно поставить строку из текущего `binary_threshold_summary.csv`, например
  `"rule_based_fuzzy"`, `"bi_encoder_zero_shot"`,
  `"cross_encoder_zero_shot"`, `"reranker_bge_v2_m3"`,
  `"reranker_qwen3_4b"`, `"reranker_qwen3_0_6b"`,
  `"reranker_jina_v3"`. Автовыбор method идёт по `cost`, затем по
  `false_merge_count`, `false_split_count` и `f1` на `dev`.
- `MY_FUSION_THRESHOLD_STRATEGY = None` — fallback-friendly режим: взять
  `threshold_weighted_cost`, если `03` подтянул объёмы продаж; иначе взять
  `threshold_cost_sensitive`.
- `MY_FUSION_THRESHOLD_STRATEGY = "threshold_weighted_cost"` — жёстко взять
  sales-weighted cost. Если weighted-строк нет, notebook упадёт, чтобы было
  видно: веса продаж не подтянулись.
- `MY_FUSION_THRESHOLD_STRATEGY = "threshold_cost_sensitive"` — обычная цена
  ошибок без веса продаж: false merge дороже false split, но каждая пара весит
  одинаково.
- `MY_FUSION_THRESHOLD_STRATEGY = "threshold_max_weighted_f1"` — диагностика
  по weighted F1; может быть смелее, чем weighted cost.
- `MY_FUSION_THRESHOLD_STRATEGY = "threshold_max_f1"` — диагностика по
  обычному F1 без веса продаж.
- `MY_FUSION_EVAL_SPLIT = "test"` — смотреть честную диагностику на test.
  Можно поставить `"dev"` для просмотра калибровочного среза или `"all"` для
  просмотра всех пар вместе.
- `MY_REQUIRE_ALL_CATEGORY_RUNS = False` — пропускать категории, которых нет в
  текущем smoke-output из `03`. Для финального полного прогона можно поставить
  `True`.
- `MY_GRAPH_GROUPING_ALGORITHM = "leiden"` — рекомендуемый финальный способ
  построить `fusion_family_id`: Leiden community detection по positive-рёбрам
  с весом из `score`. Он помогает разрезать большие chained components, где
  одна слабая связь склеивает разные товары. Для старого поведения поставьте
  `"connected_components"`.
- `MY_COMMUNITY_RESOLUTION = 0.7` — разрешение Leiden: значения выше `1`
  обычно дробят family мельче, ниже `1` делают группы крупнее.
- `MY_COMMUNITY_RANDOM_SEED = 42` — фиксирует воспроизводимый Leiden-разрез.
- `MY_COMMUNITY_EDGE_WEIGHT_COL = "score"` — колонка веса ребра; если её нет,
  все positive-рёбра считаются с весом `1`.
- `MY_COMPARE_CONNECTED_COMPONENTS = True` — сохраняет рядом старый
  connected-components baseline в audit-колонках.
- `MY_3D_CATEGORY_RUN = "auto"`, `MY_3D_GRAPH = "family"` — 3D-визуализация
  крупнейших graph components. Если установлен `plotly`, граф интерактивный;
  иначе используется статичный matplotlib fallback.

Окружение/env не используется как скрытый override для `04`: что написано в
`MY_*`, то и применяется.

`04_fusion_pack_grouping.ipynb` сохраняет:

- `fusion_components_<suffix>.csv` — товары и номера `fusion_family_id` /
  `fusion_pack_id`; эти колонки остаются финальным результатом notebook 04;
- `fusion_pair_eval_<suffix>.csv` — пары с флагами `true/pred_same_family` и
  `true/pred_same_pack`.

Если включён `MY_COMPARE_CONNECTED_COMPONENTS`, в CSV дополнительно появляются
`connected_family_id`, `connected_pack_id`, `connected_same_family` и
`connected_same_pack`. Это не новый финальный результат, а audit-baseline:
сравнение community detection с прежним connected-components поведением.
Также сохраняются metadata-колонки `fusion_grouping_algorithm`,
`fusion_community_resolution`, `fusion_community_seed` и
`fusion_community_edge_weight_col`.

`04` также показывает основную graph-quality диагностику, false links / missed
links, примеры "same family, different pack" и 3D-карту components.

`05_grouped_sku_demo.ipynb` показывает demo-flow дедупликатора уже на
реальных товарах: берёт небольшой срез похожих SKU из `mpstats_products`,
показывает дешёвые candidate pairs, строит bi-encoder embeddings, ищет
соседей через FAISS, пересчитывает пары cross-encoder и собирает группы.
Результат показывается как дерево: Level 1 — каноничный SKU с агрегатами
продаж/выручки всей группы, Level 2 — реальные SKU, входящие в эту группу.
По умолчанию cross-encoder в demo — `ft_bge_reranker_v2_m3`: это fine-tuned
BGE из server backup, поэтому его путь задаётся в первой ячейке в
`MY_FINE_TUNED_CROSS_ENCODER_MODELS`, а не в общем `model_registry`. Если
backup лежит в другом месте, поменяйте только `model_path`; для временного
zero-shot запуска можно поставить `MY_CROSS_ENCODER_MODEL` равным
`"cross_encoder_mmarco"`.
Имя таблицы в `05` не является пользовательской настройкой: demo читает
фиксированную таблицу `mpstats_products`. Лимиты demo-среза, FAISS и
cross-encoder меняются только в первой code-ячейке через `MY_*`; скрытых
`DEDUP_DEMO_*` env-overrides в notebook больше нет.
При чтении старого куба notebook применяет тот же sales-фильтр: нули и строки
ниже общего минимума `15` продаж не попадают в demo-срез. Дополнительно
сохраняет дерево в reports-папку текущего run.
Research CSV-артефакты лежат в `research/dedup/data/` или
`research/dedup/data/<slug>/`, demo-export лежит в `artifacts/reports/` или
`artifacts/reports/<slug>/`; эти рабочие файлы не коммитятся.

## 23. Безопасные правила работы

- Не отправляйте cookie в переписки и не сохраняйте его в публичные файлы.
- Не коммитьте локальную `mpstats.duckdb`, папку `data/` и рабочие CSV/XLSX-выгрузки.
- Для изменения категорий используйте CSV-справочник или редактор `Справочник`.
- Для изменения классификации используйте вкладку `Классификатор`.
- Перед повторной загрузкой большого периода сначала создайте план и проверьте количество задач.
- Не включайте `Перезаписывать БД`, если не уверены, что хотите заменить уже сохранённый срез.
- После изменения правил классификатора пересоберите нужные файлы или повторите классификацию.
- После изменения справочника создайте новый план: старый план уже содержит старый набор задач.
- Перед большой XLSX-выгрузкой проверьте количество строк в `Данные` -> `Выгрузка`; если строк больше лимита Excel, используйте CSV.
